## ADR-001: PostgreSQL as both source of truth and work queue

**Context.** Requests must be accepted fast and processed asynchronously, with
priorities, scheduled sends, retry delays, cancellation and status queries. The
scope is a ~12 hour build that reviewers must be able to run with
`docker compose up`.

**Decision.** Store notifications in Postgres and use the same table as the
queue. Workers claim work with
`SELECT ... FOR UPDATE SKIP LOCKED` inside a short transaction, mark the rows
`processing` with a lease (`locked_until`), commit, and only then call the
provider.

**Why it fits this scope.**
- **No dual-write problem.** Creating a notification *is* enqueuing it: one
  `INSERT` in one transaction. With a separate broker we would need to write the
  row and publish a message atomically (outbox pattern) or risk rows with no
  message, or messages with no row.
- **Priority, scheduling and retry delays are just columns.** `ORDER BY
  priority_rank, next_attempt_at` and `WHERE next_attempt_at <= now()` give us
  priority queues, delayed delivery and backoff without extra infrastructure.
  Kafka has no per-message delay or priority; RabbitMQ needs plugins or
  per-delay queues.
- **Cancellation is a conditional `UPDATE`.** With a broker, a cancelled
  message is still in the queue and every consumer must check a side table.
- **`SKIP LOCKED`** lets many workers claim disjoint rows without blocking each
  other.
- **One fewer moving part** for reviewers to run, monitor and reason about.

**Throughput limits (honest numbers).** A single well-tuned Postgres instance
typically sustains a few thousand claim+complete cycles per second with batched
claims. Limits come from write amplification (each notification is updated
several times: claim, complete, attempt row), WAL volume, index maintenance on
a hot table, and vacuum pressure from dead tuples. Mitigations in this design:
batched claims, a *partial* claim index that only covers claimable rows, and a
short claim transaction. Insider One's "millions per day" averages to tens of
messages per second but bursts are much higher; that is where this design
starts to strain.

**How it would evolve at Insider One scale.**
1. **Transactional outbox → Kafka.** The API still writes the notification and
   an outbox row in one transaction; a relay (or Debezium CDC) publishes to
   Kafka. Postgres stays the source of truth for status queries.
2. **Topic per channel, partitioned by recipient/tenant.** Per-channel topics
   isolate a slow SMS provider from email. Partitioning by recipient preserves
   per-recipient ordering; consumer groups scale workers horizontally.
3. **Priority via separate topics** (`sms.high`, `sms.normal`, `sms.low`) with
   weighted consumption, since Kafka has no native priority.
4. **Delays/retries via retry topics** (`sms.retry.30s`, `sms.retry.5m`) or a
   delay scheduler, plus a DLQ topic for exhausted messages.
5. **Partition the notifications table** by `created_at` (monthly) and archive
   old partitions, so the hot set stays small.

**Consequences.** Simple, correct and transactional for this scope; the queue
logic lives in a few SQL statements that are easy to test. Throughput ceiling is
lower than a dedicated broker, and the table needs vacuum attention under
sustained load.

## ADR-002: Scheduling and retries are folded into `next_attempt_at`

**Context.** Three kinds of rows become claimable at a point in time: new
(`pending`, due now), scheduled (`scheduled`, due at `scheduled_at`) and
retrying (`retrying`, due after backoff).

**Decision.** Every claimable row has a `next_attempt_at`. The claim query
selects `status IN ('scheduled','pending','retrying') AND next_attempt_at <=
now()`. There is no separate scheduler loop that flips `scheduled → pending` or
`retrying → pending`.

**Alternatives.** A periodic scheduler loop promoting rows to `pending` (the
spec allows either). It adds a moving part, a polling interval that delays
sends, and another write per row.

**Consequences.** One index, one query, no promotion lag. The statuses
`scheduled` and `retrying` remain visible to API clients, so they can still see
*why* a notification has not been sent yet. In the state diagram,
`scheduled → processing` and `retrying → processing` happen directly when due;
semantically they pass through "pending" for zero time.

**Revision: one clock decides due-ness.** The claim query compares
`next_attempt_at` with the *database's* `now()`, so every due time is now
computed on that same clock:
- immediate notifications get `now()` from the database (`COALESCE($n,
  now())`, or the transaction's `now()` for a batch written with COPY);
- retries store `now() + delay` in SQL, with the delay computed by the worker;
- only `scheduled_at`, an absolute time the client asked for, comes from
  outside.

Before this, the API's and worker's clocks were used. A flaky priority test
exposed it: rows written with the test process's clock were occasionally "not
yet due" by the database's clock, most likely because of Docker Desktop VM
clock drift. In production, API hosts with clock skew (or broken NTP) would
delay notifications by the skew. A regression test simulates an app clock
one hour fast, and fails without the fix. The same principle is why the rate
limiter uses Redis's clock (ADR-021).

## ADR-003: Text columns with CHECK constraints, plus a generated `priority_rank`

**Context.** Channel, priority, status and outcome are small closed sets.

**Decision.** Store them as `text` with `CHECK (... IN (...))` constraints.
Priority additionally has a `GENERATED ALWAYS AS ... STORED` `priority_rank`
smallint (high=0, normal=1, low=2).

**Alternatives.** Postgres `ENUM` types: adding or reordering values needs
`ALTER TYPE` and cannot run inside a transaction in older versions, which makes
migrations awkward. Storing priority as an integer only: less readable in SQL
and API payloads.

**Consequences.** Values are readable in `psql` and in logs; the database still
rejects bad values; the claim index sorts on a compact integer. Text sorting
would have put `high < low < normal`, which is why the rank exists.

**Cross-column invariants are CHECKs too** (migration 000008). Every code path
already keeps them, and the database now refuses a row that breaks them:

| Constraint | Why it matters |
|---|---|
| `processing` ⇔ `locked_until` set | A `processing` row without a lease is never reaped: stuck forever |
| `sent` ⇔ `sent_at` set | End-to-end latency and the summary read `sent_at` |
| `scheduled` ⇒ `scheduled_at` set | The API exposes it as the due time |
| `attempts <= max_attempts` | A row cannot loop past its budget |
| idempotency key ⇔ request hash | Replay vs. conflict needs both |
| `variables` ⇒ `template_id` | Variables only mean something with a template |

A bug in a future UPDATE then fails loudly in tests instead of leaving
quietly wrong rows. Two existing tests that forced impossible states (e.g.
`processing` without a lease) were fixed to produce realistic ones. The claim
query skips rows with `attempts >= max_attempts`: without that guard, one
such row would make the claim's `attempts + 1` violate the constraint and
fail the whole statement, blocking the channel (tested).

## ADR-004: Partial indexes tailored to each query

**Decision.**
- `notifications_claim_idx (channel, priority_rank, next_attempt_at) WHERE status
  IN ('scheduled','pending','retrying')`: exactly matches the claim query.
  Because it is partial, it only contains the (small) backlog, not the millions
  of `sent` rows, so it stays in memory and is cheap to maintain.
- `notifications_lease_idx (locked_until) WHERE status = 'processing'`: lets the
  reaper find expired leases without scanning.
- `(status, channel, created_at DESC, id DESC)` and `(created_at DESC, id DESC)`
  for the list endpoint's filters and keyset pagination.
- `(batch_id, created_at, id) WHERE batch_id IS NOT NULL` for batch details.

**Alternatives.** The spec's suggested `(status, channel, priority,
next_attempt_at)` full index works, but indexes every historical row and sorts
priority as text.

**Consequences.** More indexes slow writes slightly; each one is justified by a
specific query.

## ADR-005: Migrations run as a one-shot compose service

**Context.** Schema must exist before `api` and `worker` start.

**Decision.** Versioned SQL files in `/migrations` (golang-migrate format). In
compose, a `migrate` service runs `migrate up` and exits; `api` and `worker`
depend on it with `condition: service_completed_successfully`.

**Alternatives.** Running migrations inside the API on startup: couples schema
changes to a specific binary and races when several replicas start (golang-migrate's
advisory lock makes it safe, but it is still surprising). In Kubernetes the
equivalent of our approach is an init container or a pre-deploy Job.

**Consequences.** App binaries stay simple and never need DDL privileges. The
same SQL files are applied by the integration tests.

## ADR-006: Minimal dependencies, standard library first

**Decision.** `net/http` with Go 1.22 routing patterns (`GET /notifications/{id}`)
and hand-written middleware; `log/slog` for JSON logs; environment parsing by
hand. External modules only where they clearly earn their place. Runtime
dependencies: `pgx/v5` (fastest, most complete Postgres driver), `go-redis/v9`,
`google/uuid` (UUIDv7), `prometheus/client_golang`. Test-only dependencies:
`testcontainers-go` (real Postgres and Redis in tests) and `kin-openapi`
(contract tests against the spec). Migrations use the `golang-migrate` CLI
image in compose, not the Go library, so they add no module dependency.

**Alternatives.** `chi`/`gin` for routing, `viper`/`envconfig` for config. Since
Go 1.22 the standard mux handles methods and path parameters, so a router
dependency adds little.

**Consequences.** Less to audit and upgrade; a reviewer can read every line of
middleware.

## ADR-007: Configuration from environment variables only

**Decision.** All settings come from env vars with working defaults
(`.env.example` documents them). `config.Load` takes a lookup function instead
of reading `os.Getenv` directly, and collects *all* parse errors before failing.

**Consequences.** 12-factor friendly (same image in every environment);
unit-testable without touching the process environment; a misconfigured deploy
reports every problem in one log line rather than one per restart.

## ADR-008: Separate liveness and readiness probes

**Decision.** `/health/live` returns 200 whenever the process can serve HTTP.
`/health/ready` pings the dependencies concurrently with a 2s timeout and
returns 503 if a *required* one fails. The worker serves the same endpoints on
an admin port (`:8082`) and requires Postgres and Redis (it cannot send
without the rate limiter). The API requires Postgres only: Redis is optional
for it, because accepting notifications works without Redis and only the
live WebSocket stream stops, so Redis down answers 200 `degraded` and keeps
the API in rotation. (Revised: the API used to require Redis too, which
would have stopped intake during a Redis outage for no reason; found by the
interviewer agent.)

**Why.** If liveness checked the database, a Postgres outage would make the
orchestrator restart every pod in a loop: restarts cannot fix the database and
only add load when it recovers. Readiness is the right signal to stop routing
traffic.

## ADR-009: A local mock provider with failure injection

**Context.** The real target is webhook.site, whose free tier limits request
volume, and which can't easily produce 503/429 on demand.

**Decision.** `cmd/mockprovider` mimics the contract (202 + `{messageId, status,
timestamp}`) with configurable latency range, random failure rate, failure
status codes and an optional `Retry-After`. Content containing `[mock:<code>]`
(e.g. `[mock:400]`) deterministically returns that status, for demos.

**Consequences.** Reviewers can demo retries, permanent failures and the circuit
breaker offline. Integration tests use an in-process `httptest` server instead,
so they are fully deterministic.

## ADR-010: Small static binaries on a distroless base image

**Decision.** One multi-stage `Dockerfile` compiles all three binaries once
(`CGO_ENABLED=0 -trimpath -ldflags="-s -w"`), then has one final stage per
binary (`--target api|worker|mockprovider`) on
`gcr.io/distroless/static-debian12:nonroot`. Each image contains only its own
binary.

**Consequences.** Measured image sizes: api 26 MB, worker 27 MB, mockprovider
18 MB (a first version copied all three binaries into every image: 59 MB
each). The images run as non-root and contain no shell or package manager, so
there is less to attack and patch. Trade-off: no `curl` inside the container
for healthchecks; health is checked from outside (the orchestrator's HTTP
probes, or the worker's admin port).

## ADR-011: Idempotency via a unique key plus a normalized request hash

**Context.** Clients retry on timeouts. A retried create must not send a
second SMS, and a client bug that reuses a key for a different message must
not be silently swallowed.

**Decision.**
- `Idempotency-Key` header (optional, at most 255 chars) is stored in a `UNIQUE`
  column alongside `request_hash`, a SHA-256 of the *normalized* payload
  (defaults applied, `scheduled_at` converted to UTC). So omitting `priority`
  and sending `"normal"` count as the same request.
- Insert with `ON CONFLICT (idempotency_key) DO NOTHING RETURNING ...`. If no
  row comes back, load the existing row and compare hashes:
  same hash → **200** with the original resource and `Idempotent-Replayed:
  true`; different hash → **409 `idempotency_conflict`**.
- New resources return **201** with a `Location` header.
- **A replay is answered before validation.** If the key already exists, the
  stored row is returned (or 409) without re-validating the request. The
  request was valid when first accepted; re-validating it later would turn a
  successful create into a 422, e.g. a retry of a scheduled notification
  after its `scheduled_at` has passed, or after a limit was lowered. The
  client would then wrongly believe nothing was created. The hash is taken
  from the request as sent (before template rendering) for the same reason.
  The fast-path lookup is only an optimisation: the `ON CONFLICT` insert
  still decides races. (Tested for single and batch creates.)

**Alternatives.** SELECT-then-INSERT has a race: two concurrent retries both
see "no row" and both insert. A Redis `SETNX` lock adds a second system that
can disagree with the database. Storing the whole request instead of a hash
duplicates message content.

**Consequences.** Correct under concurrency (an integration test fires 20
parallel requests with one key and gets exactly one row). Keys are global (no
tenants in this scope) and never expire. In production we would scope them
per API client and purge keys after ~24h, as Stripe does.

## ADR-012: Batches are all-or-nothing, written with COPY in one transaction

**Decision.**
- Validate every item first. If any are invalid, return **422** whose
  `details` lists every failing `index` + `field`, and write nothing.
- Insert the `batches` row and all notifications in **one transaction**, using
  `COPY` for the notifications (one round trip for up to 1000 rows). IDs are
  generated in the application, so `COPY`'s lack of `RETURNING` doesn't matter.
- The batch accepts its own `Idempotency-Key` (migration 000005). A retried
  batch returns the original `batch_id` and item ids. Per-item keys inside a
  batch are not supported.
- Size limit 1..`BATCH_MAX_SIZE` (default 1000), request body limit 16 MiB.

**Alternatives.** Partial acceptance (insert valid items, report invalid
ones): clients must then diff the response to decide what to resend, and a
retry risks duplicating the accepted half. Multi-row `INSERT`: works, but it is one huge
statement with 11,000 bind parameters to parse and plan, and noticeably slower
than streaming rows with `COPY`.

**Consequences.** Simple client semantics: either the batch got in or nothing
did. A batch with one typo is rejected entirely, which is the safer default for
marketing sends.

**Note on migrations.** Batch idempotency arrived after 000002 was committed,
so it is a new migration (000005) rather than an edit. Applied migrations are
immutable; editing them would leave existing databases out of sync.

## ADR-013: Keyset (cursor) pagination on `(created_at, id)`

**Decision.** `GET /notifications` and `GET /batches/{id}` return
`{ "data": [...], "next_cursor": "..." | null }`. The cursor is an opaque
base64url token holding the last row's `(created_at, id)`. The next page uses
`WHERE (created_at, id) < ($t, $id) ORDER BY created_at DESC, id DESC`. We
fetch `limit+1` rows to know if another page exists, without a `COUNT(*)`.

**Why not OFFSET.**
1. *Performance:* `OFFSET 100000` makes Postgres read and discard 100k rows,
   so deep pages get linearly slower. A keyset seeks directly through the
   `(created_at DESC, id DESC)` index.
2. *Correctness:* this table receives inserts constantly. With OFFSET, a row
   inserted while a client pages shifts every later page, so the client sees
   duplicates or misses rows. Keyset positions are stable (tested).

`id` is the tie-breaker because every row of a batch shares one `created_at`
(the same transaction). Cost: no "jump to page 37", which an API consumer
rarely needs.

## ADR-014: UUIDv7 primary keys generated by the application

**Decision.** IDs are UUIDv7 (time-ordered), generated in Go before insert.

**Why.** Random UUIDv4 keys land all over the primary-key B-tree, causing page
splits and poor cache locality on a write-heavy table. v7 keys are appended
near the right edge, like a sequence, but are still globally unique and safe to
expose (unlike a sequential bigint, they don't reveal volume). Generating them
in the app lets batch inserts use `COPY` and lets us return ids without
`RETURNING`. `google/uuid` makes v7 ids monotonic within a process, so a
batch's id order equals its request order (unit-tested).

## ADR-015: Cancellation is a conditional UPDATE; `processing` is not cancellable

**Decision.**
```sql
UPDATE notifications SET status = 'cancelled'
WHERE id = $1 AND status IN ('scheduled','pending','retrying')
RETURNING ...
```
Zero rows means not found (404) or not cancellable (409 `invalid_state`, and
the message names the current status).

**Why.** The status check and the write are one atomic statement, so a cancel
can never race a worker's claim (which is also a conditional UPDATE). An
integration test runs the two concurrently 30 times and asserts exactly one
wins each time. `processing` is excluded because the request may already be at
the provider; claiming we cancelled it would be a lie.

## ADR-016: HTTP layer conventions

- **One error shape** everywhere: `{ "error": { "code", "message", "details" },
  "correlation_id" }`, produced by one mapper (`httpapi/errors.go`). Unknown
  errors are logged with the correlation ID and returned as a generic 500, so
  SQL or hostnames never leak.
- **400 vs 422:** 400 when the request can't be parsed (bad JSON, unknown field,
  bad query parameter); 422 when it parses but breaks a business rule.
- **404 vs 405:** an unknown path is a 404; a known path with the wrong method
  (`PUT /api/v1/notifications`) is a 405 with an `Allow` header. Go's router
  already makes that distinction but answers in plain text, so a small
  fallback (`jsonFallback`) asks the router and replies in the JSON error
  shape.
- **Strict JSON:** unknown fields are rejected (`DisallowUnknownFields`), so
  `"recipent"` fails loudly instead of being silently ignored. Bodies are
  size-limited (1 MiB single, 16 MiB batch).
- **Correlation ID:** reuse the incoming `X-Correlation-ID` only if it matches
  `[A-Za-z0-9._:-]{1,128}`, otherwise generate a UUID. The value is written to
  logs and the database, so untrusted input is restricted (no log injection).
- **Timestamps are always UTC** in responses (pgx returns the server's local
  zone otherwise).
- **Thin handlers, application service in the middle:** handlers decode and
  encode; `internal/notification.Service` validates, applies defaults and
  enforces idempotency; `internal/store` owns SQL. The service depends on a
  `Store` interface defined on the consumer side, so its decision logic is unit
  tested with a fake.

## ADR-017: Claiming work: one short statement, bounded by free send slots

**Decision.** Each channel has one claim loop and a semaphore of
`WORKER_CONCURRENCY` send slots. The loop waits for at least one free slot,
grabs up to `CLAIM_BATCH_SIZE` free slots, and claims exactly that many rows:

```sql
WITH high   AS (SELECT id FROM notifications WHERE <due> AND priority_rank = 0
                ORDER BY next_attempt_at LIMIT $high FOR UPDATE SKIP LOCKED),
     normal AS (... priority_rank = 1 ... LIMIT $normal ...),
     low    AS (... priority_rank = 2 ... LIMIT $low ...),
     picked AS (SELECT id FROM high UNION ALL SELECT id FROM normal UNION ALL SELECT id FROM low),
     fill   AS (SELECT id FROM notifications WHERE <due> AND id NOT IN (SELECT id FROM picked)
                ORDER BY priority_rank, next_attempt_at
                LIMIT $total - (SELECT count(*) FROM picked) FOR UPDATE SKIP LOCKED)
UPDATE notifications n
SET status = 'processing', attempts = n.attempts + 1,
    locked_until = now() + <lease>
WHERE n.id IN (SELECT id FROM picked UNION ALL SELECT id FROM fill)
RETURNING ...
-- <due>: status IN ('scheduled','pending','retrying') AND channel = $1
--        AND next_attempt_at <= now() AND attempts < max_attempts
```

The per-priority limits come from the fair-share planner (ADR-022); with
`PRIORITY_WEIGHTS=100,0,0` only `fill` takes rows and the claim is the
plain strict-priority `ORDER BY priority_rank, next_attempt_at`.

Each claimed row gets its own goroutine; the slot is freed when the send is
recorded. An empty claim sleeps `POLL_INTERVAL` (500ms) before trying again.

**Why.**
- **Never hold a transaction across HTTP.** The statement commits in
  milliseconds; the provider call happens afterwards. Holding row locks for a
  5-second provider call would pin connections and block vacuum.
- **SKIP LOCKED** lets N workers (goroutines or replicas) claim disjoint rows
  without waiting on each other. Tested: two workers, 300 notifications, each
  delivered exactly once.
- **Claiming only as many rows as there are free slots** means a claimed row
  never sits waiting for a send slot while its lease ticks down. It may wait
  for a rate-limit permit (ADR-021), but at most `WORKER_CONCURRENCY` rows
  per channel do, for about a second at the full rate, far inside the
  30-second lease.
- **Per-channel loops** isolate channels: a slow SMS provider cannot starve
  email sends.

**Alternatives.** One goroutine per slot each claiming one row (simpler, but
one query per message and N idle pollers per channel). `LISTEN/NOTIFY` to wake
idle workers instantly instead of polling: worth adding if 500ms latency
matters; polling is simpler and self-healing.

## ADR-018: Leases, fencing and the reaper: delivery is at-least-once

**Context.** A worker can crash (OOM, `kill -9`, node loss) after claiming a
row, possibly after the provider received the message but before we recorded
it.

**Decision.**
- A claim sets `locked_until = now() + LEASE_DURATION` (30s). A reaper loop
  in every worker (every `REAPER_INTERVAL`, 10s) moves `processing` rows with an
  expired lease back to `pending`, or to `failed` if the attempt budget is
  spent. The reaper is idempotent, so running it on every replica is safe.
- **Fencing token:** the claim increments `attempts`, and every completion
  UPDATE requires `status = 'processing' AND attempts = <my attempt>`. A worker
  that stalls past its lease cannot overwrite the result of the worker that
  re-claimed the row; it gets `ErrLeaseLost`. Its attempt is still written to
  `delivery_attempts`, because the call really happened. (Tested.)
- **Ownership is confirmed again right before the send.** A conditional UPDATE
  (`Renew`: still `processing` under my attempt number) also extends the
  lease. A worker that stalled past its lease (GC pause, slow database) while
  the reaper re-queued the row and another worker claimed it gets zero rows
  and does not call the provider; otherwise both would send. One extra
  single-row write per message. (Found by comparing with the Codex
  implementation; integration-tested with a queue that simulates the stall.)
- **The lost call is in the history** (migration 000009). The reaper writes
  the crashed claim's attempt as `outcome = 'interrupted'`, started at the
  claim (the row's `updated_at`) with no duration, because it is unknown.
  Without it, `GET /notifications/{id}` would skip an attempt number and hide
  the one fact support needs: *this message may already have been
  delivered*. If the stalled worker reports later, its real result replaces
  the placeholder (`ON CONFLICT ... DO UPDATE ... WHERE outcome =
  'interrupted'`). Interrupted calls count in `delivery_attempts_total` and
  the summary's `attempts.interrupted`, and are left out of latency
  percentiles. (Tested.)
- `LEASE_DURATION >= 2 x PROVIDER_TIMEOUT` is enforced at startup, so a healthy
  send can never outlive its lease.

**Consequence: at-least-once delivery.** If a worker dies after the provider
accepted a message but before the result was committed, the reaper re-queues
the row and it is sent again. Verified manually: `kill -9` with 8 sends in
flight → all 8 re-queued after the lease and delivered again (twice in total).
At-most-once (mark sent *before* calling) would silently lose messages
instead, which is worse for OTPs and order updates.

**How duplicates are minimised.**
1. API idempotency keys stop clients from creating duplicates (ADR-011).
2. Conditional, fenced state transitions stop *our own* components from
   double-processing a row (claim, cancel, complete, reaper).
3. Every provider request carries `X-Notification-ID: <our uuid>`, a stable
   idempotency key a real provider (Twilio, SES, FCM) can use to drop the
   duplicate on its side. This is the only way to get effectively-once
   delivery end to end.
4. The window is small: only crashes between the provider's answer and our
   commit (milliseconds) produce duplicates.

## ADR-019: Error classification and attempt accounting

**Decision.**
- *Retryable:* no HTTP response (connection errors, DNS, per-attempt timeout,
  cancellation), 5xx, 429, 408.
- *Permanent:* any other 4xx, plus unexpected 1xx/2xx/3xx. These are failed
  immediately: an identical request cannot succeed, and retrying wastes quota
  and can get us rate-limited or flagged by the provider.
- *Redirects are never followed* (`CheckRedirect` returns the 3xx as-is).
  Go's default client would turn a 301/302/303 POST into a body-less GET, so
  a 200 from the redirect target would mark a notification `sent` that the
  provider never received; a 307/308 would re-send recipient and content to
  whatever host the `Location` header names. A provider URL that redirects is
  a configuration error, so the 3xx fails the notification visibly.
- *Success:* exactly `202 Accepted`, the brief's provider contract
  (`PROVIDER_SUCCESS_STATUS`, default 202). Any other 2xx fails the
  notification as a permanent error whose message says "expected 202 (the
  message may have been delivered)". Why not accept every 2xx: a
  misconfigured URL (a proxy, a login page) can answer 200, and counting
  that as `sent` would lose the message silently; a loud `failed` shows up in
  metrics and the dead-letter list. Why permanent and not retryable: the
  provider may have taken the message, so an automatic retry could deliver it
  twice; an operator decides with the error in front of them. The brief tells
  us to configure webhook.site to answer 202, so a correct setup never hits
  this. (Revised: an earlier version accepted any 2xx.)
- *A different 2xx also counts against the provider in the circuit breaker*
  (ADR-024), although the notification itself fails as permanent. It is a
  contract or configuration problem that will hit every message: without
  this, permanent errors reset the breaker's streak and a whole backlog
  drained to `failed` at 100/s (found by the interviewer agent). Now the
  breaker opens after a few, and the rest wait in the queue for the fix.
- An attempt is counted when it is *claimed* (that number is the fencing
  token). A job released on graceful shutdown before its send started has the
  attempt refunded. A job reaped after a crash keeps it, because we can't know
  whether the provider got it, and that attempt is recorded as `interrupted`
  (ADR-018).
- `Retry-After` (seconds or HTTP-date) is honoured when it asks for longer than
  our own delay.

## ADR-020: Graceful shutdown

**Decision.** On SIGTERM the worker:
1. stops claiming (claim loops exit),
2. lets in-flight provider calls finish, for up to `SHUTDOWN_TIMEOUT` (15s),
3. then cancels the rest. A cancelled call is recorded as a retryable attempt
   (it may have reached the provider), not silently dropped,
4. releases any job whose send had not started (attempt refunded),
5. keeps the admin/health server up until the drain finishes.

Provider calls run on a context derived with `context.WithoutCancel`, so the
signal itself doesn't abort a call that is about to succeed. Result writes use
a fresh 5s context, so a result is recorded even during a hard stop.
`SHUTDOWN_TIMEOUT > PROVIDER_TIMEOUT` is enforced so a normal call always
fits, and compose's `stop_grace_period` (20s) exceeds `SHUTDOWN_TIMEOUT`.
Verified manually: SIGTERM with 8 sends in flight → all 8 recorded `sent`
before exit.

## ADR-021: Distributed rate limiting with a Redis sliding window of sends (Lua)

**Context.** The brief says "maximum 100 messages per second per channel".
The limit must hold across *all* worker replicas, not per process, it must
hold *as the provider sees it* (the provider counts requests when they
arrive, which we cannot observe), and waiting workers must not spin.

**Decision.** One sorted set per channel in Redis (`ratelimit:{<channel>}`),
one entry per send that still counts. A send's entry counts **while the
request is in flight and for one second after it returns**:
1. Right before each provider call, the worker runs `acquire.lua`: drop
   entries whose score is one second old, and grant a slot only if fewer than
   100 remain. The new entry's score is `now + max send time` (provider
   timeout + 1s), so it counts for as long as the request may be in flight.
2. As soon as the call returns (success or not), `done.lua` lowers the score
   to the finish time (`ZADD XX LT`), so the slot frees one second later.
3. A full window returns a wait (capped at 100ms, since a send may finish
   early), so a waiting worker sleeps instead of polling Redis.
4. A worker that dies mid-send never calls `done`; its entry still expires
   one second after the max send time.

**Why this holds at the provider.** The provider receives each request at
some moment between our start and its answer. Take any 1-second window of
arrivals and the request in it whose slot was granted last. Every other
request in the window either was still in flight at that grant or had
finished less than a second before it (it arrived inside the window, which
started less than a second before that grant), so it still held its slot:
there were at most 99 of them. So the provider never sees more than 100 in
any second, whatever the network delays. The script reads **Redis's clock**
(`TIME`), so clock skew between worker hosts cannot inflate the rate.

**Where it sits in the worker.** The claim is sized by free send slots
(ADR-017); the permit is taken in `process`, after the ownership check and
immediately before the HTTP call, and released when the call returns.
Every permit is used, so nothing is ever refunded.

**Defaults.** 100 per second per channel (`RATE_LIMIT_<CHANNEL>_PER_SECOND`).

**Measured.** At the provider (`TestRateLimit_ProviderNeverSeesMoreThan100PerSecond`,
three replicas, backlog and bursty trickle; `..._SlowOwnershipCheck...`, a
400ms database hiccup): busiest 1-second window exactly 100. Limiter alone,
4 replicas over 2s with instant sends: 200 grants. Two workers against a fast
fake provider: 200 sends in 2s.

**Revised, twice.**
1. The first version was a token bucket (100/s, burst 10): any 1-second
   window could hold 109 grants (measured 110). Burst 1 wasted capacity
   (about 77/s).
2. The second was a sliding window of *grants*, taken before the claim and
   refunded with `ZPOPMAX`. The failure-hunter agent broke it twice: a refund
   removed another replica's entries (103 in a second), and because the time
   between grant and send varied (claim, ownership check, a cold
   connection), the provider saw up to 160 sends in one second (200 with a
   slow database).

**Failure mode: fail closed.** If Redis is unreachable, the job is handed
back unsent after a poll interval (the send slot stays busy meanwhile, so
this does not become a claim-release loop). Getting throttled or banned by
the provider is worse than a short pause, and the worker's `/health/ready`
turns red so the outage is visible.

**Alternatives.**
- *Token bucket*: O(1) memory, but either exceeds 100 in some second
  (burst > 1) or wastes capacity (burst 1).
- *Counting grants, not sends* (the second version): full 100/s, but only
  "at most 100 grants per second"; the provider can see more.
- *Fixed window counter* (`INCR` + `EXPIRE`): simplest, but allows 2x the
  rate across a window boundary.
- *GCRA / `redis-cell`*: elegant, but needs a Redis module.
- *Per-process limiter (`x/time/rate`)*: needs `rate / replicas` per process
  and breaks whenever replicas scale.

**Trade-offs.** Holding a slot for the request's duration plus one second
caps throughput at about `100 / (1 + provider latency in seconds)`: about
95/s at 50ms, 83/s at 200ms. The brief sets a maximum, so we stay under it
rather than risk going over; with a fast provider the full 100/s is reached.
Each send costs two Redis round trips (acquire, done), negligible next to
the provider call. Memory is at most 100 small entries per channel.

## ADR-022: Priority with weighted fair sharing, so low is never starved

**Context.** The brief asks for priority support (high, normal, low) and
nothing more specific. Rate limiting is what makes priority matter: during a
flash-sale burst a channel is capped at 100/s, and priority decides *which*
100 go first (OTPs and transactional messages before marketing). The first
version used strict priority: every due `high` before any `normal`, every
`normal` before any `low`. Under sustained `high` traffic that starves `low`
forever, and nothing in the brief asks for that.

**Decision.** Each channel shares its sends between priorities by weight,
`PRIORITY_WEIGHTS=70,20,10` by default, while more than one priority is
waiting.
- The worker plans every claim with *smooth weighted round robin* (the
  algorithm nginx uses for upstream weights): each slot goes to the priority
  with the most credit, which then pays the sum of the weights. Over any 10
  slots that is exactly 7 high, 2 normal, 1 low, interleaved, and the credit
  carries across claims, so the share holds when a saturated worker claims one
  row at a time (`worker/fairshare.go`).
- The claim takes each priority's reserved slots from that priority, oldest
  due first, and gives every slot a priority could not use (nothing due) to
  the rest of the backlog in strict order (`queue.Quota`). Reserved slots are
  a floor, not a cap: with only `high` traffic, `high` gets everything; when
  the queue is short, the order is the same as strict priority. Because the
  unused share goes by priority, not by weight, `normal` and `low` alone
  split 90/10, not 67/33: `normal` keeps its 20 and takes `high`'s 70. That
  is deliberate: every priority has a guaranteed minimum, and spare capacity
  favours the more important messages.
- `100,0,0` switches sharing off (strict priority).

**Evidence.**
- Each reserved part filters one `priority_rank` and orders by due time, so it
  is an ordered scan of the partial `notifications_claim_idx` with no Sort
  node (`EXPLAIN`: Index Scan → LockRows → Limit). The strict version measured
  0.05 ms on 205k rows; the shared claim runs four such scans.
- `TestPriority_LowIsNotStarvedByAHighFlood`: one `low` behind 30 due `high`
  is sent within the first 10 sends; with `100,0,0` it is send #31.
- `TestFairShare_*`: 70/20/10 over 100 slots in claims of 1, 3 and 10.

**Alternatives.**
1. *Strict priority* (the first version): simplest, but starves `low`.
2. *Aging* (a row moves up one priority for every N minutes it waits): the
   sort key changes with time, so the index cannot supply the order and every
   claim sorts the whole due backlog, which is exactly when the backlog is
   large.
3. *Separate queues/topics per priority* with consumer quotas, in a Kafka
   design (ADR-001).

**Consequences.** During a flood, `high` gets at least 70% of the channel,
not 100%: an OTP may wait a little longer while marketing still moves. That
is the trade for a bounded wait for every message. The weights are per
replica; with several worker replicas the shares hold on average. The
weights are one setting, so a product team that wants strict priority back
can have it.

## ADR-023: Exponential backoff with full jitter, honouring Retry-After

**Decision.** After the k-th failed attempt (retryable errors only):

```
ceiling(k) = min(RETRY_MAX_DELAY, RETRY_BASE_DELAY * RETRY_BACKOFF_FACTOR^(k-1))
delay(k)   = uniform random in [0, ceiling(k))            # "full jitter"
delay(k)   = max(delay(k), min(Retry-After, 1h))          # provider knows best
```

Defaults: base 2s, factor 2, cap 5m, `MAX_ATTEMPTS` 5. So the ceilings before
attempts 2-5 are 2s, 4s, 8s, 16s. The worst case is about 30s of waiting
(expected ~15s) before a notification is failed.

**Why full jitter.** An outage fails thousands of messages at the same instant.
With plain exponential backoff they all retry at +2s, +4s, +8s in synchronized
waves, and each wave hits the recovering provider with the whole backlog.
Drawing each delay uniformly from the whole window spreads the retries out.
AWS's "Exponential Backoff and Jitter" analysis found full jitter does the
least total work and clears the backlog fastest. The unit test checks both
the bounds (`0 <= delay < ceiling`) and that 2400 draws really spread out.

**Retry-After.** If a 429/503 carries `Retry-After` (seconds or HTTP-date), we
wait at least that long; the provider knows its own capacity. It is bounded
at 1 hour so a broken header can't park messages indefinitely.

**Why the budget is short.** Backoff is for *transient* blips (one bad request,
a brief spike). A real outage is the circuit breaker's job (ADR-024): it stops
claiming entirely, so a 30-minute outage doesn't burn anyone's 5 attempts.
Together they keep latency low for blips without dead-lettering everything
during an outage.

**Alternatives.** "Equal jitter" (half fixed, half random) guarantees a
minimum wait but spreads load less. "Decorrelated jitter" is a good
alternative with similar results. A fixed delay is easy to reason about, but
it gives synchronized retry storms.

## ADR-024: Circuit breaker per channel

**Decision.** Each worker keeps one breaker per channel:

```
closed    --(BREAKER_FAILURE_THRESHOLD consecutive retryable failures)--> open
open      --(BREAKER_COOLDOWN elapsed)--> half_open
half_open --(single probe succeeds)--> closed
half_open --(probe fails)----------> open (cooldown restarts)
```

- **What counts:** only retryable failures (5xx, 429, timeouts, network). A
  permanent 4xx means the provider is up and rejected *that* request, so it
  resets the streak like a success. A send aborted by our own shutdown is not
  counted.
- **While open, nothing is claimed.** Notifications stay `pending`/`retrying`
  with their attempt budget intact (tested: 7 of 10 untouched at
  `attempts = 0`). A job already claimed when the breaker trips is released
  before sending, with its attempt refunded. The claim loop sleeps for the
  remaining cooldown instead of polling.
- **Half-open allows exactly one probe** across the channel's claim loop. If no
  row is due, the probe permit is returned, so the next iteration can try again.
- **Results belong to the period they started in.** Every state change bumps a
  generation number; each claimed job carries the generation it was claimed
  in. A job whose generation is no longer current is released unsent, and a
  result from an older generation is ignored. Otherwise a slow send from
  before the breaker opened could finish during half-open and close the
  breaker before the real probe answered (reachable with a cooldown shorter
  than the provider timeout; found by comparing with the Codex
  implementation; unit-tested).
- Transitions are logged (warn on open, info on close) and exposed through a
  hook that feeds the `circuit_breaker_state{channel}` metric.

**Measured.** Integration test (threshold 3, sequential sends): exactly 3
provider calls, then none during the cooldown, then 10/10 sent once the
provider recovered. Live run (threshold 5, concurrency 10, mock 100% 503):
14 calls before the breaker stopped traffic. Sends already in flight when it
trips still complete, so the worst case per worker is
`threshold + concurrency` calls.

**Per process, not shared.** Each replica learns provider health on its own
traffic. With R replicas, an outage costs up to R x (threshold + concurrency)
calls before all of them open. That's a few dozen requests, which is acceptable.
A breaker shared in Redis would open everywhere at once, but it adds a Redis
dependency to every send decision, and a cross-replica race on the half-open
probe. Worth it only at large replica counts.

**Revision: what "consecutive" means (found by the end-to-end run).** The
first version counted any N retryable failures in a row. Running the e2e
scenario against a long-lived worker opened the email breaker after just two
fresh failures. There were two reasons:
1. *Stale streaks:* failures from a much earlier run (with no email successes
   since) were still counted, so two new ones reached the threshold.
2. *Poison messages:* a single notification that always gets a 503 produces N
   "consecutive failures" from its own retries and pauses the whole channel,
   though the provider is fine for everyone else.

The fix: the streak counts **distinct notifications**, and failures more than
`BREAKER_FAILURE_WINDOW` (1m) apart start a new streak. A real outage
fails many different notifications within milliseconds, so it still trips
the breaker immediately (the integration test still opens it at exactly 3
calls). Both cases have regression tests.

**Alternatives.** Failure-*rate* windows (e.g. open at >50% failures over 20
calls with a minimum volume, as Hystrix and resilience4j do) are more robust
to interleaved successes, but harder to reason about and test. A
consecutive-distinct-failures streak with a time window is enough for a single
upstream per channel.

## ADR-025: Failed notifications are the dead-letter set; manual retry

**Decision.** `failed` (permanent error or budget exhausted) is terminal for
the worker and acts as the dead-letter queue: queryable with
`GET /notifications?status=failed`, with `last_error` and the full attempt
history. `POST /notifications/{id}/retry` redrives one:

```sql
UPDATE notifications
SET status = 'pending', max_attempts = attempts + <MAX_ATTEMPTS>,
    next_attempt_at = now(), locked_until = NULL
WHERE id = $1 AND status = 'failed'
```

**Why `max_attempts` grows instead of `attempts` resetting to 0.**
`delivery_attempts` has `UNIQUE (notification_id, attempt_no)`, and the attempt
number is the fencing token (ADR-018), so it must only ever increase. Raising
the budget gives the same "fresh 5 attempts" without rewriting history.
Anything not `failed` gets 409, the same conditional-UPDATE pattern as cancel.

**Future work.** A bulk redrive (`POST /notifications/retry?batch_id=...` or by
error type) for after a provider outage or a fixed configuration bug.

## ADR-026: Observability: metrics, summary and correlation

**Metrics (Prometheus, `GET /metrics` on the API and the worker admin port).**

| Metric | Type | Labels | Source |
|---|---|---|---|
| `notifications_created_total` | counter | channel, priority | API (replays not counted) |
| `http_requests_total`, `http_request_duration_seconds` | counter, histogram | method, route, status | API |
| `notifications_sent_total` | counter | channel | worker |
| `notifications_failed_total` | counter | channel, reason (`permanent_error`, `max_attempts`, `lease_expired`) | worker |
| `delivery_attempts_total` | counter | channel, outcome | worker |
| `delivery_latency_seconds` | histogram | channel | worker (one provider call) |
| `end_to_end_latency_seconds` | histogram | channel | worker (created → sent) |
| `due_to_sent_seconds` | histogram | channel | worker (due → sent: our own delay) |
| `queue_depth` | gauge | channel, priority, status | worker, refreshed from Postgres |
| `circuit_breaker_state` | gauge (0/1/2) | channel | worker |
| `leases_reaped_total` | counter | result | worker |

Design choices:
- **One registry per binary** (not the global default), each exporting only
  what that process produces, plus Go runtime and process collectors.
- **Bounded label cardinality.** HTTP metrics are labelled with the mux
  *pattern* (`GET /api/v1/notifications/{id}`), never the raw path, which
  contains ids and would create one time series per notification (tested).
  The metrics middleware is innermost because `ServeMux` writes `r.Pattern`
  into the request it receives, and outer middleware pass it a copy.
- **The engine reports through a small `worker.Observer` interface** defined
  next to the code that uses it, so the worker has no Prometheus dependency and
  tests can plug in fakes.
- **Two latencies for scheduled sends.** `end_to_end_latency_seconds` and the
  summary's `end_to_end_latency_ms` run from creation to sent, as the brief
  defines them, so a scheduled wait is included. `due_to_sent_seconds` starts
  at `scheduled_at` when that is later, so a send scheduled for tomorrow
  doesn't hide a slow queue behind a day of intended waiting. (An earlier
  version measured end-to-end from the due time; the Codex comparison pointed
  out that this departs from the brief's definition.)
- **`queue_depth` comes from Postgres** (`GROUP BY channel, priority, status`
  over non-terminal rows, every 15s), because the database is the only place
  that knows the true backlog. Every replica exports the same value, so
  dashboards aggregate with `max`, not `sum`. Every combination is written
  (zero-filled), so a drained series reads 0 instead of keeping its last
  value (tested).
- Series that alerts depend on (`notifications_sent_total`,
  `circuit_breaker_state`) are pre-created at 0, so "no data" never hides a
  stuck worker.

**`GET /api/v1/metrics/summary?window=1h`** is for humans without Prometheus:
current queue depth, plus sent/failed counts, success rates, attempt outcomes
and p50/p95 provider and end-to-end latency over the window, overall and per
channel. It is computed **from Postgres, not from in-process histograms**:
- it covers every worker replica, while a process's histograms only see that
  process;
- `percentile_cont` gives exact percentiles over the window, where Prometheus
  histogram quantiles are bucket interpolations;
- the window is arbitrary (1m-168h) without pre-aggregation.

`GROUP BY ROLLUP (channel)` produces per-channel and overall percentiles in one
query. Migration 000006 adds time-column indexes so the cost is proportional to
the window, not the full history. Rates with no data are `null`, not 0% or
100%.

**Correlation.** The `X-Correlation-ID` header (validated, or generated) goes
into the request context and every API log line, is stored on the row, and is
attached to every worker log line and every provider request. Verified live:
one batch with `trace-demo-42` → 1 API log line, 363 worker lines and 363
provider requests (one per attempt), all carrying the id. Log keys are fixed
constants: `correlation_id`, `notification_id`, `batch_id`, `channel`,
`attempt`.

**Measured live** (300 notifications, 20% injected failures): the worker's
Prometheus counters and the DB-backed summary agree exactly (300 successes +
63 retryable failures = 363 attempts).

## ADR-027: The OpenAPI spec is a tested contract

**Context.** A hand-written spec drifts from the code unless something forces
it not to.

**Decision.** `api/openapi.yaml` (OpenAPI 3.0.3) documents every endpoint,
schema, error code and example, and three tests keep it honest:
1. `TestOpenAPISpecIsValid` loads and validates it with kin-openapi, including
   checking every `example` against its schema.
2. `TestOpenAPISpecMatchesRoutes` compares the spec's operations with the
   router's route table (`httpapi.RoutePatterns`) in both directions: no
   undocumented endpoint, no documented endpoint that doesn't exist.
3. In the API integration suite, **every response** (status, headers, body) is
   validated against the matching operation, and undocumented status codes fail.
   The ~30 existing API tests became contract tests without new test code.

Both checks were mutation-tested: deleting the retry endpoint from the spec
fails (2), and changing `CreateBatchResponse.total` to a string fails (3)
with `Error at "/total": value must be a string`.

Swagger UI (compose, port 8081) serves the same file. "Try it out" calls the
API on port 8080, a different origin, so the API has a small CORS middleware
with an explicit allow-list (`CORS_ALLOWED_ORIGINS`, default
`http://localhost:8081`) that answers preflights before any other middleware.

**Alternatives.** Generating the spec from code annotations (swaggo) keeps
the two in sync but produces weaker docs and puts comments everywhere.
Generating server code from the spec (oapi-codegen) is a strong option for a
larger team; for this size a hand-written spec plus contract tests is simpler
to read and explain.

## ADR-028: Templates are immutable and rendered at create time

**Decision.**
- `POST /api/v1/templates` stores a Go `text/template` body (`Hi
  {{.first_name}}`). It is compiled on creation, so syntax errors fail
  immediately rather than on the first send. The response lists the
  **required variables**, found by walking the parse tree: every field read,
  including in both `{{if}}` branches (unit-tested).
- **Only variables and conditionals.** The same walk rejects everything but
  text, `{{.name}}` / `{{.order.id}}` and `{{if .x}}...{{else}}...{{end}}`.
  `text/template` has built-in functions and loops: `{{printf "%099999999d"
  1}}` allocates ~100 MB, and nested `{{range}}` over a large array spins the
  CPU. Either lets one API request hurt the service, and a notification
  template does not need them (message logic belongs in the caller). Found by
  probing the API; unit-tested with each rejected construct.
- A notification gives either `content` or `template_id` + `variables`. The API
  renders the template **at create time** and stores the result as `content`
  (plus `template_id` and `variables` for traceability). Workers only ever see
  final text.
- The rendered text goes through the same channel rules as hand-written content.
  An SMS template that renders to 171 characters is a 422 on `content`.
  Missing variables are reported together ("missing required variables: code,
  name"), not one per request; `missingkey=error` stays on as a safety net.
- Templates are **immutable** (no update endpoint), so rendering at create
  time is deterministic. The idempotency hash includes `template_id` and
  `variables`.
- A batch loads each distinct template once (`templateCache`), not once per
  item.

**Why render in the API rather than the worker.** Errors such as missing
variables or rendered text that is too long reach the client synchronously as
a 422, instead of failing later as a `failed` notification nobody is watching.
The stored row shows exactly what was sent. And the worker stays a dumb,
fast pipe.

**Alternatives.** Rendering in the worker would allow late-bound data (e.g.
current loyalty points), but turns client mistakes into asynchronous failures.
Mutable templates would need versioning, so that queued notifications don't
change meaning; that's future work if marketing teams need it.

**Safety.** Besides the syntax restriction above, the template body is capped
at 20,000 characters and the request body at 1 MiB (16 MiB for a batch).
Rendering stops as soon as the output is certainly over the channel's limit
(4 bytes per character, so 641 bytes for a 160-character SMS). Without that, a
body that repeats one variable 3,333 times renders ~63 KB per item, and a
1000-item batch allocated ~374 MB before the length rules rejected it (found
in review; a unit test now measures the allocation).

## ADR-029: Live status stream: Redis pub/sub fanned out over WebSocket

**Decision.**
- Every status change publishes a small JSON event to the Redis pub/sub channel
  `notifications:status`:
  - the API publishes `pending`/`scheduled` on create (a whole batch in one
    pipelined round trip), `cancelled` on cancel, and `pending` on manual retry;
  - the worker publishes `processing` when it starts an attempt, and `sent`,
    `retrying` or `failed` once the result is committed.
- Each API replica holds **one** Redis subscription and fans events out to its
  WebSocket clients (`GET /ws?notification_id=|batch_id=`) through an in-memory
  hub. Replicas need no coordination: each sees every event and keeps the ones
  its clients asked for.
- **Best-effort, by design.** Pub/sub is at-most-once: a disconnected client
  misses events. That's fine for a live view. A client that reconnects reads
  the current state from the REST API, which remains the source of truth.
  Publishing has a 500ms timeout and never fails the API call or the
  delivery that triggered it.
- **Back-pressure:** each client has a 256-event buffer. A client that falls
  further behind is disconnected (close 1008, "reconnect and read current
  state") rather than slowing delivery to everyone else.
- **Lifecycle:** pings every 30s keep idle connections alive through proxies.
  On shutdown the hub closes every socket with 1001 (going away), since
  `http.Server.Shutdown` doesn't track hijacked connections. Browser origins
  come from `CORS_ALLOWED_ORIGINS`.

**Measured.** In a browser on the Swagger UI origin, a batch of 2 produced
`pending` x2, `processing` x2, `failed` (the `[mock:400]` item) and, after a
random mock 500, `retrying` then `processing#2`, all within ~2s. Integration
tests cover publisher → Redis → hub → WebSocket client with a batch filter,
and graceful close.

**Alternatives.**
- *Redis Streams* (`XADD`/`XREAD`) give replay from an ID, so a client could
  resume after reconnecting. Worth it if clients must not miss events; it costs
  stream trimming and per-client offsets.
- *Postgres `LISTEN/NOTIFY`* avoids Redis, but its payload limit (8 kB) and
  delivery while a transaction is open are awkward, and it would add load to
  the database.
- *Server-Sent Events* would be simpler than WebSockets for one-way traffic;
  WebSocket was asked for and leaves room for client messages (e.g. changing
  the filter) later.

## ADR-030: Distributed tracing across the asynchronous queue

**Context.** A notification's life spans two processes and an arbitrary wait:
the API request, rows in Postgres, then one or more worker attempts and
provider calls, possibly minutes later. Logs joined by `correlation_id` show
*what* happened; a trace shows *where the time went*.

**Decision.** OpenTelemetry with OTLP/HTTP export to Jaeger (compose,
UI on :16686):
- **Spans:** `otelhttp` on the API (server spans renamed to the route pattern;
  health, metrics and `/ws` excluded), `otelpgx` on every query, `redisotel` on
  Redis, a `deliver <channel>` consumer span per attempt in the worker, an
  `otelhttp` transport on the provider client (which also sends `traceparent`),
  and `otelhttp` on the mock provider.
- **Crossing the queue:** the API stores the request's W3C `traceparent` in a
  new `notifications.trace_parent` column (migration 000007; batches share the
  batch request's). Each worker attempt starts its span as a **child** of that
  stored context, so a single trace reads API → DB → attempt 1 → retry wait →
  attempt 2 → provider. The OTel messaging convention also allows span
  *links*; a parent/child relationship was chosen because it renders as one
  readable timeline in Jaeger, which is what an on-call engineer needs.
- **Sampling without noise:** `ParentBased(NoOrphanClientSpans)`. Spans with a
  sampled parent are kept. Root spans are kept unless they are Client spans:
  those are the worker's background chatter (claim polls every 500ms per
  channel, rate-limiter calls, reaper and queue-depth queries), which would
  otherwise each become a one-span trace. Measured: after ~90 claim polls the
  worker had exactly one trace in Jaeger, rooted at the API request.
- **Log correlation:** API and worker log lines carry `trace_id`.
- **Off by default:** tracing is enabled only when the standard
  `OTEL_EXPORTER_OTLP_ENDPOINT` is set, so tests and local runs pay nothing.

**Tested.** Unit: sampler decisions and traceparent round trip. Integration:
an incoming `traceparent` is stored on the row; a worker delivery span has the
stored trace ID and parent span ID, and the provider receives a `traceparent`
for the same trace. Live: one seeded batch produced a single trace with
spans from `api`, `worker` and `mockprovider`.

**Trade-offs.** Five extra modules (OTel SDK and exporter, otelhttp,
otelpgx, redisotel). A trace stays open as long as a notification keeps retrying,
so very long traces are possible (the retry budget caps them). At production
volume we'd sample (head-based 1-5%, or tail-based in an OTel Collector so
that every failed delivery is kept).
